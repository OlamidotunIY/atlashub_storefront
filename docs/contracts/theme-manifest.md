# Theme developer contract: React app, routes, settings and versioning

**Status:** Design proposal, API surface illustrative (not an existing npm package).

## Required developer experience

Official creator scaffold uses Vite, React, TypeScript and React Router Framework Mode. Developer can write their own responsive pages, components, CSS/Tailwind, fonts, icons, animations, navigation and *approved* client logic. No visual drag-and-drop theme editor in initial scope.

The scaffold declares exactly which public storefront routes it implements. Normal route examples: \`/\`, \`/collections/:handle\`, \`/products/:handle\`, \`/cart\`, \`/pages/:slug\`, \`/404\`. Storefront route parameters and public data come from platform-attested host/store context; developer route cannot select arbitrary merchant by query string. Actual route requirements, error/loading states and compatibility are versioned.

## Manifest example (schema to be implemented)

\`\`\`json
{
  "schemaVersion": "1.0",
  "themeId": "fashion-studio",
  "version": "1.0.0",
  "creatorId": "creator-123",
  "name": "Fashion Studio",
  "engine": "react-router-vite",
  "sdkCompatibility": ">=1.0 <2.0",
  "pages": ["home", "collection", "product", "cart", "content", "not-found"],
  "capabilities": ["public-catalog", "public-assets", "cart", "checkout-redirect"],
  "locales": ["en"],
  "settings": {
    "logo": {"type":"asset:image","label":"Store logo","default":"/theme/defaults/logo.svg"},
    "favicon": {"type":"asset:image","label":"Favicon","default":"/theme/defaults/favicon.png"},
    "primaryColor": {"type":"color","label":"Primary color","default":"#2563EB"},
    "heroTitle": {"type":"text","label":"Homepage title","default":"Discover our collection","maxLength":120},
    "heroImage": {"type":"asset:image","label":"Hero image","default":"/theme/defaults/hero.webp"},
    "productsPerPage": {"type":"integer","label":"Products per page","default":12,"min":4,"max":48},
    "featuredCollection": {"type":"reference:collection","label":"Featured products","default":null,"required":false}
  }
}
\`\`\`

Developer-supplied *asset defaults* are immutable theme-bundle references validated by build; merchant overrides are separately stored Asset IDs owned by the specific storefront. \`null\` is an allowed explicit optional default for a merchant-specific collection that cannot be guessed across stores; renderer must have safe fallback UI. No missing mandatory defaults. Schema/version signatures/digests are generated by the platform, not trusted from developer input.

## Runtime SDK concept (illustrative)

\`\`\`tsx
import { useThemeSettings, atlashub } from "@atlashub/storefront-sdk";

export function FeaturedProducts() {
  const { logo, heroTitle, primaryColor } = useThemeSettings();
  const { data, isLoading, error } = atlashub.products.useList({limit:8});
  if (isLoading) return <p>Loading products...</p>;
  if (error) return <p>Products unavailable.</p>;
  return <main style={{color: primaryColor}}>
    <img src={logo} alt="Store logo" />
    <h1>{heroTitle}</h1>
    {data?.items.map(p => <ProductCard key={p.id} product={p}/>)}
  </main>;
}
\`\`\`

Final public SDK names and APIs must be generated/maintained against Java OpenAPI or explicitly versioned contracts; code above is conceptual. \`atlashub.products.list/get\`, \`collections.list/get\`, \`cart.get/add/update/remove\`, \`checkout.start\`, \`theme.settings.get\` are examples, not implemented functions.

## Merchant setting semantics

- Create \`StorefrontConfigRevision\` from developer defaults merged with merchant-owned overrides, with strict schema and fallback behavior.
- Merchants use dashboard forms generated from settings schema: logo, icon, colors, font choices, banners, copy, layout toggles, categories, product collection references, social links and localized copy **only where developer declares them**. Developer determines layout.
- Validate types, URLs, references, file ownership, allowed CSS values, media formats/sizes and text lengths. HTML/JS custom code fields denied initially.
- A merchant edit first creates DRAFT configuration and preview, not immediate published change. Publish immutably snapshots selected release+config revision.
- Theme upgrade maps old keys to new schema via safe migration, previews unknown/deprecated keys, preserves compatible merchant override values and allows rollback. No silent replacement of configured logo/images.
- Configuration is distinct from catalog: product descriptions, stock and price remain authoritative in Java commerce.

## Theme compatibility/release metadata

\`Theme\`, \`ThemeVersion\`, \`SourceArchive\`, \`BuildReport\`, \`ThemeRelease\`, \`ReleaseManifest\`, \`ThemeInstallation\`, \`StorefrontConfigRevision\`, \`Publication\`. IDs unique and tenant/creator constrained; release immutable with semver + SDK/schema compatibility, content hash, content security metadata, approved runtime bundle and static asset digests.

## Build contract

Source archive excludes \`node_modules\` and local secrets; lockfile and allowlisted package manager expected. Isolated CI installation and lifecycle scripts restrictions, security dependency scan, file bounds and SSR Worker compatibility. The platform, not the creator, computes final integrity hash and signing. Creator can upload a new version, never overwrite an approved content-addressed release.

No arbitrary Node.js process, database credential, secret, filesystem write or uncontrolled outbound API from deployed theme. Untrusted browser JavaScript still needs CSP and separate checkout origin.
